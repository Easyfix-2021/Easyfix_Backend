Getting started

The Partner API is a small, stable REST surface. Most integrations use four endpoints: read your service catalogue, create a job, upload photographs, and check status — with webhooks pushing progress to you so you never have to poll.

The Partner API is a small, stable REST surface. Most v2 integrations use three endpoints: read your service catalogue, create a job with its photographs in a single call, and check status — with webhooks pushing progress to you so you never have to poll.

Base URLs

Production
https://backend.easyfix.in/api/integration/v1v2
QA — build against this first

Every path in this document is relative to that base. All requests are HTTPS; plain HTTP is not served.

Your first call

# Confirm your credentials reach us and see your service catalogue
curl -u 'YOUR_USERNAME:YOUR_PASSWORD' \
  'https://qa.backend.easyfix.in/api/integration/v1v2/services'
Moving from the old API?

Only the base URL changes. Every endpoint path, header, request body and response body stays exactly as it is today, as do your credentials, service IDs, job IDs and webhook events. See What changed.

v2 is opt-in — nothing on v1 stops working today

If you already integrate on v1, nothing breaks and nothing is urgent. v1 is unchanged and fully supported. We do intend to retire the two-step image flow — upload each image, then create the job carrying their ids — but no date is set, and any retirement will carry a formal notice period. Every other v1 endpoint stays as it is.

v2 changes exactly one thing: creating a job can carry its images in the same request. Everything else on this page — authentication, the response envelope, dates, errors, the service catalogue, job status, lookups and every webhook — is byte-for-byte identical across the two versions. Move an integration to v2 when the single-call create is worth it to you, and not before.

Authentication

Every endpoint uses HTTP Basic authentication. Send your username and password on each request; there is no token exchange, no login call and nothing to refresh.

Authorization: Basic <base64 of "username:password">

Your credentials identify your organisation. Everything you can see is automatically scoped to it — you will only ever read your own jobs, your own prices and your own invoices, and you cannot reference another partner's records even by ID.

Missing or wrong credentials return 401 with a WWW-Authenticate header:

{ "status": "401", "message": "Invalid credentials", "data": null }
Keep credentials server-side

These credentials can create real jobs that dispatch real technicians. Call the API from your backend only — never from a browser, a mobile app, or anywhere the username and password ship to a device.

Rate limit

1,200 requests per minute per set of credentials — roughly 20 per second, far above normal integration traffic. Exceeding it returns 429; wait a moment and retry.

Conventions

Response envelope

Almost every response — success or failure — uses the same three-key envelope, with your real payload under data. The single exception is job creation, which returns the job object at the top level; that asymmetry is preserved from the previous API so existing integrations keep working.

{
  "status":  "200",        // string, not a number
  "message": "OK",
  "data":    { /* the payload, or null on failure */ }
}

status mirrors the HTTP status code and is always a JSON string. Parse the HTTP status code, the status field, or both — they never disagree.

Dates and times

WhereFormatExample
REST request & response bodiesDD-MM-YYYY HH:mm17-10-2026 14:30
Date-only query parametersYYYY-MM-DD2026-10-17
Webhook payloadsYYYY-MM-DD HH:mm:ss2026-10-17 14:30:00
All times are IST

Every timestamp we send or accept is India Standard Time (UTC+05:30), written as local wall-clock time with no timezone suffix. Do not apply an offset when parsing, and send us IST rather than UTC — a job booked for 17-10-2026 09:00 is a 9am appointment in the customer's own morning.

Identifiers

  • Job ID — ours, returned when you create a job. Use it for every follow-up call.
  • reference_id — yours. Send your own order or ticket number when creating a job and we echo it back on every response and webhook, so you can reconcile without storing our IDs.
  • service_id — a line on your rate card, from the catalogue. It is specific to your organisation, not a global product code.

Errors

Failures use the same envelope, with a human-readable message and data: null.

{ "status": "400", "message": "Unknown city \"Gurgoan\"", "data": null }
CodeMeaningWhat to do
400The request was understood but a value is unusable — an unknown city, a missing jobId.Fix the value. Retrying unchanged will fail again.
401Credentials missing, wrong, or deactivated.Check the header; contact us if it persists.
403The record exists but belongs to another partner.Check the ID against your own records.
404No such record for your organisation.Treat as "not found" — do not retry.
429Rate limit exceeded.Back off briefly, then retry.
500Something failed on our side.Safe to retry with backoff. Send us the time and reference_id if it repeats.
Retrying job creation

Job creation is not de-duplicated. If POST /jobs times out you cannot know whether the job was created, so check before retrying — call /jobs/tracking and look for your reference_id. A blind retry dispatches a technician twice.

Two response shapes

This endpoint returns one of two shapes, decided by how your account is configured. Both carry identical service_type objects — the only difference is whether they are wrapped in categories.

{
  "status": "200", "message": "OK",

Handle both, and you never have to care

Cache it, refresh it daily

The catalogue changes only when your contract does. Cache it rather than calling it before every booking — but do refresh it daily, because a service_id withdrawn from your rate card is rejected at booking time.

Create a job

The main endpoint. One call books a technician visit: who the customer is, where they are, when they want it, and which contracted services apply.

Planned for deprecation — move to v2 when you can

Nothing changes for you today. This endpoint works exactly as documented and no retirement date is set. But the two-step flow — upload each image, collect its imageId, then create the job carrying them — is the part of v1 we intend to retire, and it will be given a formal notice period well before anything stops working.

The replacement is v2’s combined create: the job payload and up to five images travel in one request. A partner attaching three photographs goes from four round trips to one, and there is no window where uploaded images exist but the job does not.

New integrations should start on v2. Existing ones can move whenever convenient — the job payload is identical field for field, so the only change is the envelope.

Create a job, with its images

The main endpoint. One call books a technician visit — who the customer is, where they are, when they want it, and which contracted services apply — and attaches the photographs that go with it.

Why v2 exists

On v1, a partner with three photographs makes four calls: three uploads to collect imageId values, then the create call carrying them. Each is a round trip, and the job does not exist until the last one lands — so a partner whose second upload fails is left holding orphan images and no job, with no job ID to retry against and nothing to show a customer.

v2 is one request. The job and its images go up together, and an image that fails never costs you the job.

POST/jobs

Creates a job and attaches up to five images. Content-Type: multipart/form-data

Parts

NameTypeDescription
payload *stringThe job, as a JSON string. Exactly the body v1's POST /jobs takes — every field identical.
imagesbinaryOne image. Repeat the part once per image — maximum 5 parts, maximum 10 MB each.
The job body is unchanged

The payload part is the same JSON v1 accepts — the same fields, the same required set, the same defaults, the same DD-MM-YYYY HH:mm dates. Rather than repeat all twenty rows here, read them on v1's field table; following that link switches this page to v1.

jobImageIds still works exactly as it does on v1, so images you uploaded earlier can be adopted at creation as well — the images parts are attached alongside them, not instead of them.

Repeating one part name is how an HTML <input type="file" multiple> posts a file selection, so every HTTP client and every language supports it natively. There is no base64 encoding and no JSON envelope wrapped around the bytes — the files go up as files.

Example

curl -u 'USER:PASS' \
  -F 'payload={"jobDesc":"Treadmill install","jobType":"Installation","requested_date":"20-08-2026 10:00","reference_id":"YOUR-ORDER-10231","customer":{"name":"Priya Sharma","mobile":"9999578666"},"address":{"address":"Sector 44, near Huda City Centre","city":{"city_name":"Gurgaon"},"pinCode":"122001"},"service_type":{"services":[{"service_id":24055}]}};type=application/json' \
  -F 'images=@front.jpg' \
  -F 'images=@serial-plate.jpg' \
  'https://backend.easyfix.in/api/integration/v2/jobs'
No images? Then skip multipart entirely

If you have no photographs to send, POST plain application/json with just the job body — byte for byte a v1 create call, aimed at the v2 URL. Multipart is only needed when there are actually files to carry.

Response — 201 Created

The same body v1's create returns, plus an images array — and, as on v1, at the top level with no status / message / data envelope, alongside a Location header pointing at the new job.

  "reference_id": "YOUR-ORDER-10231",
  "customer": { "id": 55, "mobile": "9999578666", "name": "Priya Sharma" },
  "address": { "address": "Sector 44, near Huda City Centre", "city": { "city_id": 3, "city_name": "Gurgaon" }, "pinCode": "122001" },
  "images": [
    { "imageId": 408397, "image": "18082026110412_front.jpg", "originalName": "front.jpg", "status": "attached" },
    { "imageId": 408398, "image": "18082026110412_serial-plate.jpg", "originalName": "serial-plate.jpg", "status": "attached" }

Store id. As on v1, fields with no value are omitted rather than sent as null, so treat every key as optional when parsing.

The images array

FieldTypeDescription
imageIdintegerOur ID for the stored image. Present only when status is attached.
imagestringThe stored filename.
originalNamestringThe filename you sent — match on this to tell the entries apart. Entries are returned in the order you sent them.
statusstring"attached" or "failed".
reasonstringWhy it failed. Present only when status is "failed".
A failed image does not fail the request

The job is created either way. By the time an image is being stored the job already exists and you need its ID — replying 500 would leave you re-posting a job we have already booked, and dispatching a technician twice. So an image that cannot be stored comes back as an entry in the array rather than as an error:

{ "originalName": "serial-plate.jpg", "status": "failed", "reason": "Storage rejected the file" }

Check the array, not just the HTTP code. A 201 means the job exists; it does not on its own mean every photograph landed.

Retry a failed image on its own against the job ID you now hold, using v1's POST /jobImage/addJobImages with JobId set — that endpoint is unchanged and works against jobs created on either version. Nothing needs re-creating.

Errors

The request is rejected outright — and no job is created — in these cases:

CodeCauseWhat to do
400More than 5 images parts.Send five, create the job, then add the rest with v1's image upload against the returned job ID.
400An image larger than 10 MB.Compress or resize it. The limit is per file, not per request.
400The payload part is missing, or is not valid JSON.Send it as a JSON string in a part named exactly payload.
400An unknown city in the job body.Check the name against /cities, or send city_id.
401Credentials missing, wrong, or deactivated.Check the Authorization header. See Authentication.

Every other failure behaves exactly as it does on v1 — same codes, same envelope, same meanings. See Errors.

Retrying is still not de-duplicated

As on v1, a create that times out leaves you unable to tell whether the job was booked. Check before retrying — call /jobs/tracking and look for your reference_id. A blind retry dispatches a technician twice, and re-uploads the photographs with it.

A new job starts as Pending for scheduling and moves on once a technician accepts — you will receive a TechAssigned webhook when that happens.

Job status

GET/jobs/jobStatus

The current status of one job.

Query parameters

NameTypeDescription
jobId *integerThe ID returned when the job was created.

Response

{
  "status": "200",
  "message": "OK",
  "data": { "jobId": 212251, "currentStatus": "Pending to start" }
}
This endpoint always returns HTTP 200

Failure is signalled in the body, not the HTTP status. An unknown job — or one belonging to another partner — returns:

{ "status": "300", "message": "Incorrect jobId", "data": { "jobId": 0 } }

Branch on status, not on the HTTP code. Omitting jobId altogether returns an empty object, {}.

Prefer webhooks over polling

This endpoint is for reconciliation and support lookups. For live progress, register webhooks — you get each change as it happens instead of discovering it on your next poll.

Upload images

Attach photographs to a job — the product to be installed, the site, a damage report.

Planned for deprecation — move to v2 when you can

Nothing changes for you today, and no retirement date is set. This endpoint will keep working, with a formal notice period before that changes.

If you use this to attach images at booking time, v2’s combined create replaces it entirely: images ride along with the job payload in a single request, so there is no separate upload to fail and no orphaned image if it does.

Attaching an image to a job that already exists — a later site photograph, a damage report — stays here, and remains the right endpoint for that on both versions.

Uploading before the job exists

When you have photographs at order time, upload them first and attach them as you book:

  1. Upload each image without JobId, and keep the returned imageId.
  2. Pass those IDs as jobImageIds in POST /jobs.

Only images you uploaded yourself, and which are not already attached to a job, can be adopted this way.

Lookup & tracking

Supporting endpoints. All are scoped to your organisation and use the same envelope.

GET/jobs/tracking

Your recent jobs with their current status. Optional status and limit (default 50, maximum 500). Use this to find a job by your own reference_id after a timeout.

GET/jobs/history

Jobs within a date range. Takes startDate and endDate as YYYY-MM-DD.

GET/jobs/{id}

Full detail for one job — status, job type, requested and scheduled times, the assigned technician's name, and your reference.

DELETE/jobs/{id}

Cancels a job. Fires the CancelJob webhook. Cancel as early as you can — a technician already travelling may still attract a visit charge under your contract.

GET/easyfixers/availability-status

Whether a slot can be served, before you commit to it. Takes pincode, requestedDate and timeSlot; returns {"isAvailabil": "Yes"} or "No".

GET/cities

Serviceable cities with their city_id values — useful for validating an address before booking.

GET/clientInvoice

Your invoices, optionally filtered by startDate and endDate. Includes billing period, amounts due, payment state and links to the invoice PDF and master sheet.

REST responses give a human-readable currentStatus. Webhooks carry the numeric status. Both describe the same lifecycle.

Webhooks

Rather than polling, give us an HTTPS endpoint and we will POST to it whenever one of your jobs moves. This is how most partners keep their own systems current.

Setting them up

Send us, for each event you want:

  • The callback URL — HTTPS, reachable from the public internet.
  • An optional authorization value, which we send verbatim as the Authorization header on every delivery so you can verify the call is ours. Include any scheme you need — if you want Bearer abc123, give us exactly that string.

You can register a different URL per event or point them all at one endpoint and branch on the event field.

Delivery

PropertyValue
MethodPOST
Content typeapplication/json
Timeout15 seconds
Retries3 attempts — immediately, then after 30 seconds, then after 5 minutes
SuccessAny 2xx response
What your endpoint should do

Reply 200 immediately, then process. Acknowledge first and do your own work asynchronously — slow handlers hit the 15-second timeout and get treated as failures.

Expect duplicates. A retry after a timeout can deliver an event you already handled. De-duplicate on jobData.id plus event.

Ignore unknown fields. We add fields to payloads without notice. Never fail on a key you do not recognise.

Events

EventFires when
TechAssignedA technician has accepted the job in their app. This is acceptance, not merely allocation — the visit is confirmed.
TechStartThe technician has reached the customer and submitted the start PIN.
RescheduleTechThe technician, or the appointment date or time, has changed.
TechVisitCompleteWork was completed at the location.
TechVisitInCompleteThe visit ended without completion. revisitDate and the reason fields explain why.
CancelJobThe job was cancelled, at any point.

What changed

If you already integrate with core.easyfix.in/v1, this is everything you need to look at. Your credentials, service IDs, job IDs and webhook event names are unchanged.

One line of code

Change your base URL. For almost every integration that is the whole migration — endpoint paths, headers, request bodies and response bodies are unchanged, including the status label strings, the 201-with-no-envelope reply from job creation, and the {} that jobStatus returns for a missing jobId.

The one exception: if you book through /jobs/newJob, its response now matches /jobs instead of using the envelope. See Create a job.

BeforeAfter

Everything else Unchanged — paths, Basic Auth credentials, headers, request bodies, response bodies, status strings, HTTP codes, service IDs, job IDs, webhook events and payloads.

Improvements you get for free

None of these require a change on your side.

  • Pricing comes from your rate card. Previously the amount in your request was written to the job, so a request sending only service_id — exactly what this document shows — booked the line at zero. Every line is now priced from your contract.
  • Webhooks retry. A failed delivery is retried twice more, after 30 seconds and 5 minutes. Previously a single failure was lost silently, with no record kept.
  • Webhook images are downloadable URLs rather than bare filenames.
  • Uploaded images are protected. jobImageIds now only adopts images you uploaded yourself, so nobody else's photograph can be attached to your job.
  • Past appointment dates are no longer silently moved an hour into the future.
